# 基于已执行记录的改进方向

[返回测试与证据总览](README.md)。本文保留 2026-09-27 的分析；后续批次与公开结果请从总览进入。

2026-09-27。本次发布补充证据与校正统计口径，安装包仍为 v0.3.2。以下是后续优化建议，并非已实现功能或已测得的新版本收益。

## 已得到支持的价值

- GPT-6 Luna high 的 [72 次对照](luna-high-2026-09-27/REPORT.md)中，ReuseBeacon 与 search-first 各 21/24 次外部断言全过；ReuseBeacon 的总主机工具调用少 16.7%、总执行时间少 16.1%、总未缓存输入少 51.1%。这是本套任务的效率结果，不能外推为所有任务的固定收益。
- 已上传的 GLM/ZCode [iteration-5](results/iteration-5.json) 和 [iteration-7](results/iteration-7.json)中，三个 cron 任务重复的 ReuseBeacon 平均报告 total tokens 比无 Skill 低 86.3%；过程记录显示成熟库复用有价值。这里重新计算了 JSON，未在本轮独立复现这些 GLM 会话。此 token 口径不能与 Luna 未缓存输入合并。
- 两批记录都展示了实际 Skill 使用与实现复用。接下来应提高关键决策的可靠性，保留小任务的直接退出能力。

## 优先级和最小改动

| 优先级 | 证据与问题 | 建议改动 | 如何验收 |
| --- | --- | --- | --- |
| P1：减少误判后自建 | [Issue #4](https://github.com/xtltt56-cmd/reusebeacon/issues/4)报告了一次把 VTIMEZONE 能力判断为不可用后手写较大实现的案例；当前 selection.md 已有失败输入与适配检查，单纯重复规则无益。 | 将决定 Build 的核实要求移到实际做选择的位置，替换重复措辞：决定性的“不支持”判断须有对应版本的可运行反例或明确 API 证据；先检查配置或小适配。仅在准备放弃候选时触发。 | 复测一个库原生支持、一个小适配可解决、一个确实不支持的案例；记录误拒绝率、自建代码量、测试和成本，允许真正必要的 Build。 |
| P1：继续降低小任务成本 | 本轮 CSV 中位未缓存输入 R 14,804、N 12,806（+15.6%）；Excel R 16,846、N 14,092（+19.5%）。已上传 v0.3.2 CSV 三次的平均报告 total tokens 差为 +8.6%，不是固定 +5%。 | 保持入口处已有的小修复出口；仅在实测发现仍加载无关参考、重复搜索或重复验证时收紧。优先测量隐式触发是否能跳过孤立修复，减少不必要加载；不增加新的检查表。 | 分开测“强制加载的最小开销”和“原生触发的避让率”。按文件读取、外部查询、必要测试次数和未缓存输入定位开销，不能只以文档字数推算成本。 |
| P2：用总成本决定库与标准库 | [Issue #3](https://github.com/xtltt56-cmd/reusebeacon/issues/3)和 #4 的巨型 JSON 案例有候选反转，不能一概要求 ijson 或一概要求标准库。 | 将优先顺序明确为满足需求时的偏好；在已有性能硬约束且关键差异未明时，做最小代表性测试，记录输入规模、后端、版本和约束。复用已测证据。 | 对真实输入形态比较端到端实现成本、峰值内存和耗时；达到预算后停止，不做每项任务都跑的性能竞赛。 |
| P2：验证结果驱动交付 | 本轮 T5 存在冻结题面与评分器冲突；旧记录三次将 `pass_rate=1` 与 `649/652` 同时记录。 | 先修订下一套评测的题面与评分契约；最终结果由机器输出生成，区分任务门槛通过与所有断言全过。精确一致性仅在需求规定时要求，不把全量标准测试常态化。 | 先让参考实现验证题面与断言一致，再冻结。失败、跳过、未执行分开统计；原实验评分器与分数保持原样。 |
| P2：原生触发及弱提示发现 | 现有两批都是指路式强制加载；Luna 的共同指令本就鼓励复用，多题点名已有依赖，T7 显式要求使用浏览器 Skill。 | 用真实仓库中的需求描述测试，不在题面提示包名或 Skill 名；自然呈现已安装 Skill 的正常元信息。解释/小改动作为应跳过样本。 | 同模型 GPT-6 Luna high、同预算、独立目录、预先固定题目和外部测试；同时记录漏触发、误触发、正确复用、成功率和成本。条件有冲突先修评测，不能靠出题偏袒 R。 |

先做一个有明确假设的最小修改，再用相关难例和少量小任务回归对照旧版本；出现有效收益后才扩展全矩阵。已有 72 次运行可作历史基线，但提示、工具或宿主变化后应重新运行匹配基线，不能直接把新条件与旧耗时相减。

## 已上传记录的口径审计

[review_prior_records.py](review_prior_records.py)重新读取 [results/](results/)，输出 [prior-records-audit.json](prior-records-audit.json)。它核对现有 JSON，未替代原始工具轨迹审查或项目输出重跑。

- 已归档 iteration-1 至 iteration-7 共 **85 条互异运行记录、9 个题型**。iteration-5/6/7 共 **51 条**。旧文档中的约 87 条、8 个题型及 42 条版本矩阵与已上传文件数量不一致，引用时应明确批次范围。
- 三条 CommonMark 记录同时含 `pass_rate=1` 和 `649/652`，分别在 iteration-3 S、iteration-4 S、iteration-7 R。二元字段可能记录总体验收门槛，不能据此称每条断言均通过。保留原 JSON，在报告层说明。
- v0.3.2 CSV 三次每组的均值为 R 215,621.7、N 198,594.3 个报告 total tokens，即 **+8.6%**；前两次或单次结果不能作为稳定平均值。相同三次 cron 的差为 **−86.3%**。均为小样本、指定任务结果。
- 本轮 Luna 的 **72/72 分数复现一致**与 **63/72 全部外部断言通过**是不同指标；T5 的九次部分通过仍保留。不能把两种通过率混写，也不能把两套 token 口径加总。

## 当前不应扩充的内容

不新增固定平台预检、不恢复强制 GitHub 登录、不强制每题搜索所有渠道、不常态运行全量规范套件、不扩大默认 Skill 安装数量。当前证据支持精简决策节点和更有区分力的测试；不支持为了显得全面而增加整套规则。
